## What this is

`source-postgresql` is a CDC (Change Data Capture) source node for the **InthHub** platform, written in Go. It does an initial snapshot of configured Postgres tables/views, then streams ongoing changes via logical replication (slot + `pgoutput` plugin), publishing everything to a Kafka topic.

## Commands

```bash
go build ./...      # compile check
go vet ./...         # static analysis
cp .env.example .env # fill in with your local Postgres/Kafka details
go run .             # run locally (starts pipeline + /healthz and /metrics on :9999)
```

There are no `*_test.go` files in this repo — validation is done by running against a real Postgres/Kafka locally (see `testdata/`), not via `go test`.

### Local test loop (`testdata/`)

- `testdata/partitioned_table.sql` — creates an example `PARTITION BY` table to snapshot.
- `testdata/seed_bulk.sql` — bulk-loads rows to exercise snapshot pagination.
- `testdata/cdc_stream.sh` — continuously generates insert/update/delete to exercise CDC streaming.
- `testdata/reset_test_env.sh <slot> <output_topic> <state_topic> <broker>` — drops the replication slot + publication, recreates the Kafka topics (state topic with `cleanup.policy=compact`), and truncates the test table, for a clean re-run. Run it against the docker-compose stack with `go run .` stopped first.
- `docker-compose.homelab.yaml` — local Postgres 16 (`wal_level=logical` pre-set) + Kafka/Zookeeper/Connect stack used for the above.

## Architecture

### The critical constraint: everything lives in `process.go`

This is an InthHub "Go Function" node. The platform only builds `process.go` — it does not support internal packages, and `main.go` is **generated by the platform**, not something you edit there. Consequences for how this repo is organized:

- **`process.go`** is the only file that ships to the platform. All logic — config loading, Postgres catalog inspection, publication/slot management, snapshot, CDC streaming, slot monitoring — lives in this single ~1700-line `package main` file, deliberately not split into packages.
- **`main.go`** in this repo is a *local scaffold only*, not what runs on the platform. It reconstructs just enough of the platform's contract (`initVars()`, `process()`, `ProcessResult`, `sendDlq`, `/healthz`, `/metrics` on :9999) to let `go run .` work locally. If the platform's real `main.go` ever has a different signature for these hooks, adjust the few call sites at the bottom of `process.go` — don't try to change what ships as `main.go`.
- `.env`/`.env.example`, `docker-compose.homelab.yaml`, and `testdata/` are local-only scaffolding and never ship to the platform.

### Inverted control flow vs. normal InthHub nodes

Normal Go Function nodes are `consumer -> transform -> producer` over a message from `INPUT_TOPIC`. This node's source of data is Postgres itself, not Kafka, which inverts the usual hook usage:

- **`initVars(ctx, log)`** is the real entry point. Since it's the only hook the platform guarantees calling once before the consume loop starts, the entire pipeline (slot bootstrap, initial snapshot, CDC streaming, slot monitor) is launched from here as a background goroutine (`runPipelineForever`, guarded by `sync.Once`) using a fresh `context.Background()` — not the `ctx` passed into `initVars`, since the pipeline must outlive that call.
- **`process(topicName, value, key, headers, log)`** is nearly a no-op — it always returns `nil, nil`. It exists only to satisfy the generated `main.go`'s contract. A low-frequency Cron Input must be wired into the pipeline on the platform side purely so the platform's "every Transform needs an Input" validation passes; its tick content is ignored.

### Bootstrap sequence (`runPipelineOnce` in `process.go`)

1. `inspectTables` resolves each `SOURCE_TABLES` entry against `pg_class` (plain table, partitioned root, or view).
2. `ensurePublication` creates/extends the Postgres publication to cover CDC-capable tables (not views — Postgres emits no WAL for views).
3. `ensureReplicationSlot` creates the replication slot with `CREATE_REPLICATION_SLOT ... EXPORT_SNAPSHOT`, producing a consistent LSN (`ConsistentPoint`) and a reusable snapshot name.
4. `runInitialSnapshot` snapshots tables/views using that exported snapshot (`SET TRANSACTION SNAPSHOT`), so there's no gap or overlap with where CDC streaming picks up.
5. `replicator.run` streams from `ConsistentPoint` onward.

On restart, steps 2-4 are skipped (slot/publication already exist) and streaming resumes from `confirmed_lsn` saved in `STATE_TOPIC`. If the process dies mid-snapshot of a large table, it resumes from the last saved primary-key cursor, not from scratch (`tableSnapshotState`/`pipelineState` in `process.go`).

### Checkpointing without external storage

State (confirmed LSN + per-table snapshot progress) is persisted to a compacted Kafka topic (`STATE_TOPIC`, default `{OUTPUT_TOPIC}-state`) rather than any external store. `STATE_TOPIC` must be created manually with `cleanup.policy=compact` — unlike `OUTPUT_TOPIC`, which the InthHub platform auto-creates and injects.

### Partitioned table snapshotting

For `PARTITION BY` tables, `discoverPartitions` finds physical child partitions via `pg_inherits`, and `snapshotPartitionedRoot` reads up to `SNAPSHOT_WORKERS` of them in parallel, each on its own connection/transaction, all importing the *same* exported snapshot (same technique as `pg_dump --jobs`) — published under the root table's name. Real parallelism is capped by the actual partition count, not just the config value.

`SNAPSHOT_WORKERS` (absolute ceiling 12, `maxSnapshotWorkers`) and `SNAPSHOT_FETCH_SIZE` (absolute ceiling 20000, `maxSnapshotFetchSize`) are clamped in code regardless of env var value, because peak memory scales with `workers × fetch_size × row width` — one worker holds a full batch in memory. Values above either ceiling are clamped with a logged `warn`, not rejected. There is also a combined ceiling on the *product* `SnapshotWorkers × SnapshotFetchSize` (`maxSnapshotBatchRows`, 160,000 — matching the documented reference config of 8×20000), since the two individual ceilings alone still allow their worst-case combination (12×20000=240,000); when the product is exceeded, `SNAPSHOT_FETCH_SIZE` is the one reduced, not `SNAPSHOT_WORKERS`, since partition parallelism is what buys real Postgres I/O throughput. `applyContainerMemoryLimit` additionally sets a soft GC ceiling (`runtime/debug.SetMemoryLimit`) from the cgroup's memory limit at startup (unless `GOMEMLIMIT` is already set), to make GC react before hitting the pod's hard limit under allocation spikes — but this only helps once there's garbage to reclaim, it can't shrink genuinely live data below the pod's limit.

Snapshot rows are also never held in two representations at once: `fetchAndEncodeBatch` (keyset-paginated tables/partitions) and `streamEncodedBatches` (views, shared by initial snapshot and periodic refresh) encode each row straight from `pgx.Rows` into a `kafka.Message` as they scan, instead of building a `[]map[string]any` batch first and converting it to messages in a second pass — that double-buffering was the main driver of snapshot-time OOMs on wide tables. All message encoding (key+value marshal, headers) funnels through the single `encodeMessage` helper.

Permission-wise, partitioned tables need `SELECT` granted on *each child partition* individually — a `GRANT` on the root is not sufficient and not what's read from. See README's "Checklist — tabela particionada" for the exact grant statements, including `ALTER DEFAULT PRIVILEGES` for future partitions.

### Message format

- Key: flat JSON of PK columns only (e.g. `{"id": 123}`); views have no reliable PK so publish with an empty key.
- Value: flat, typed JSON of all columns for insert/update/snapshot; **empty** for delete (tombstone convention expected by downstream sink connectors).
- Headers: `table`, `op` (`r`=snapshot, `c`=insert, `u`=update, `d`=delete), `ts`, `lsn`. Kept out of the value so the value stays 100% flat for sink connectors that transact it into another database.

### Config loading

All config comes from `os.Getenv` inside `loadSourceConfig` (`process.go`) — see the README's "Variáveis de ambiente" table for the full list, defaults, and which vars are Secret-backed vs. plain on the InthHub platform. Notable non-obvious ones:
- `resolveKafkaBrokers()`: `KAFKA_BROKERS` takes priority; falls back to `INTHUB_KAFKA_CONNECTION` (auto-injected when the pipeline uses a Kafka → Conexões connection) when unset.
- `PG_POOL_MAX_CONNS` defaults to `SnapshotWorkers + 6` — must accommodate snapshot workers running concurrently plus the slot monitor and view-refresh loop.

### Resilience

No per-message reprocessing exists here (no consumer group/offset model — it's a background loop), so `runPipelineForever` restarts the whole pipeline with exponential backoff (5s to 2min cap) on any error, resuming from the last checkpoint in `STATE_TOPIC`.
